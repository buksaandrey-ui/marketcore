## 1. Общие положения и стратегия продукта

### 1.1. Миссия продукта
**MarketCore** — это центр командования селлера. Это не дашборд «ради дашборда», а система принятия решений (**Decision Support System, DSS**), которая замыкает полный цикл: `данные → инсайт → действие → результат`. Платформа берёт на себя рутинные операции (изменение цен, ставок, поставки) и высвобождает ментальный ресурс селлера для стратегии.

### 1.2. Целевая аудитория (ICP — Ideal Customer Profile)

| Сегмент | Оборот в мес. | Ключевая боль | Ценность MarketCore |
|---|---|---|---|
| **Starter** | до 1 млн ₽ | Не понимает юнит-экономику, упускает сезонность | Автоматический калькулятор + прогноз OOS |
| **Growth** | 1–10 млн ₽ | Не успевает управлять ставками, теряет позиции | Hourly Bidding + мониторинг локализации |
| **Pro** | 10–50 млн ₽ | Много SKU, нужна централизация и аналитика конкурентов | Полный пакет + парсинг + API-интеграции с ERP |
| **Enterprise** | 50+ млн ₽ | Кастомные сценарии, White-label, выделенный менеджер | Dedicated instance + SLA 99.95% |

### 1.3. Ключевые бизнес-метрики (Product KPI)

- **Time-to-Value (TTV):** от регистрации до первого автоматического действия — **< 15 минут**.
- **Активация:** подключённый кабинет + настроенное правило биддинга в первые 24 часа — **≥ 60%**.
- **Retention D30:** **≥ 45%**, Retention D90: **≥ 30%**.
- **NRR (Net Revenue Retention):** **≥ 115%** (рост ARPU за счёт апсейла тарифов).
- **Churn mo/mo:** **< 5%**.

### 1.4. Принципы проектирования
1. **Mobile-first, не mobile-last.** Все критичные операции (правка ставки, цены, аппрув поставки) должны выполняться с телефона за ≤ 2 тапа.
2. **Zero-noise UI.** Каждый пиксель на экране обязан нести функциональную или семантическую нагрузку. Декор исключён.
3. **Explainable automation.** Любое автоматическое решение системы должно иметь читабельное обоснование: «Снизил ставку на 12%, так как CR упал на 18% за последние 4 часа».
4. **Fail-safe by default.** Автоматика никогда не может сделать необратимое действие без guardrails (лимиты, подтверждения, rollback).

### 2.3. Принципы разделения сервисов

- **Bounded contexts** (DDD): Auth, Account, Catalog, Pricing, Bidding, Forecast, Analytics, Billing.
- **Async-first коммуникация** между сервисами через Kafka. Синхронные REST-вызовы — только в рамках одного bounded context.
- **CQRS** для аналитики: записи летят в OLTP, читаются из ClickHouse (через Debezium CDC).
- **Idempotency:** все внешние операции (изменение ставки, цены) идут с `Idempotency-Key` для безопасных ретраев.

#### 3.1.2. Rate-limiting стратегия (WB)
WB применяет лимиты на уровне **токена** и **эндпоинта**. Пример: 100 req/min на контент, 3 req/sec на статистику рекламы.

```
┌─────────────────────────────────────────────────────────────┐
│  Стратегия: Token Bucket + Circuit Breaker + Exponential BO │
├─────────────────────────────────────────────────────────────┤
│  1. Redis хранит счётчики: wb:ratelimit:{seller_id}:{endpoint}│
│  2. Перед вызовом — INCR + TTL. Если overflow → задержка     │
│     по формуле t = base * 2^attempt + jitter(0..500ms)       │
│  3. После 5 последовательных 429 — Circuit Breaker OPEN      │
│     на 60 секунд, алерт в Sentry + уведомление пользователю  │
└─────────────────────────────────────────────────────────────┘
```

#### 3.4.3. Логика сопоставления с нашими ценами

Алгоритм **price-matching decision engine**:

```python
def decide_price_action(our_sku, competitor_snapshot, rules):
    """
    our_sku: {price, rrc, min_margin_price, stock, category}
    competitor_snapshot: [{sku, price, rating, stock, seller_id}, ...]
    rules: {strategy: 'beat_by_X' | 'match' | 'premium_gap' | 'ignore'}
    """
    # 1. Фильтр «релевантные конкуренты»
    relevant = [c for c in competitor_snapshot
                if c.rating >= 4.5
                and c.stock > 0
                and abs(c.price - our_sku.price) / our_sku.price < 0.30]

    if not relevant:
        return NoAction("Нет релевантных конкурентов")

    # 2. Определяем benchmark
    median_price = percentile([c.price for c in relevant], 50)
    min_competitor = min(relevant, key=lambda c: c.price)

    # 3. Применяем стратегию
    if rules.strategy == 'beat_by_X':
        target_price = min_competitor.price - rules.delta_rub
    elif rules.strategy == 'match':
        target_price = median_price
    elif rules.strategy == 'premium_gap':
        target_price = median_price * (1 + rules.premium_pct / 100)

    # 4. Guardrails: не ниже min_margin_price
    target_price = max(target_price, our_sku.min_margin_price)

    # 5. Не меняем, если дельта < 0.5% (шум)
    if abs(target_price - our_sku.price) / our_sku.price < 0.005:
        return NoAction("Изменение в пределах шума")

    return PriceChangeAction(
        from_price=our_sku.price,
        to_price=target_price,
        reason=f"Benchmark: {median_price}₽, стратегия {rules.strategy}",
        requires_approval=(abs(target_price - our_sku.price) > our_sku.price * 0.10)
    )
```

**Важно:** изменения > 10% от текущей цены требуют ручного подтверждения (guardrail против флэш-крашей цены из-за кривых данных парсинга).

### 3.5. Рекламный инструментарий

#### 3.5.1. Wildberries: Автореклама и Поиск

- **Автореклама (auto-campaign):** ставка задаётся в CPM, применяется ко всей кампании.
- **Поиск (search-campaign):** ставка на фразу (keyword-level).
- **Каталог, карточка, рекомендации:** отдельные типы с собственной логикой биддинга.

**Ключевые методы нашей обёртки:**

```
POST /internal/ads/wb/campaign/{id}/bid
Body: {
  "campaign_type": "auto" | "search",
  "target_cpm": 250,
  "strategy_ref": "peak_hours_v2",
  "guardrails": { "min_cpm": 150, "max_cpm": 500 },
  "idempotency_key": "uuid-v4"
}
```

Внутри сервис:
1. Проверяет guardrails.
2. Логирует изменение в `ads_bid_history` (append-only).
3. Делает вызов WB API.
4. Публикует событие `ads.bid_changed` в Kafka.
5. При ошибке — retry с экспоненциальной задержкой, после 3 ошибок — алерт.

#### 3.5.2. Ozon: Трафареты (Sponsored Products)

- Работа на уровне **товара в кампании** (PUT `/api/client/campaign/{id}/products`).
- Ставка в **рублях за 1000 показов** (CPM) или **за клик** (CPC) — зависит от типа кампании.
- Поддержка **автостратегий Ozon** + наш overlay через `bid_price`.

**Ключевая особенность:** Ozon требует batch-обновления (до 1000 товаров за один вызов). Наш сервис группирует изменения в окно 30 секунд, чтобы минимизировать количество API-запросов.

### 3.6. Обработка ошибок внешних API

| Класс ошибки | Action | User notification |
|---|---|---|
| `401 Unauthorized` | Отключить кабинет, пометить token_expired | Push + email: «Обновите ключ API» |
| `403 Forbidden` | Записать в лог, без ретраев | В карточке кабинета индикатор ⚠️ |
| `429 Rate Limit` | Backoff → ретрай до 5 раз | Тихо, только в dev-логах |
| `5xx Server Error` | Backoff → ретрай, Circuit Breaker после 10 подряд | Баннер в UI, если > 5 мин |
| `Network / Timeout` | Backoff → ретрай | Только если > 3 мин |

## 4. Модуль 2. Факторы ранжирования и Индекс локализации

### 4.1. Зачем это нужно
Позиция в выдаче = функция от множества сигналов. Большинство селлеров работают с одним-двумя (CPM и цена), но реальный кумулятивный эффект даёт **параллельная работа со всеми факторами**. MarketCore превращает неявные сигналы в measurable KPI и подсказывает приоритетное действие.

### 4.2. Модель факторов ранжирования

```
                        POSITION IN SEARCH
                              ▲
                              │
   ┌──────────────────────────┴──────────────────────────┐
   │                                                      │
   │   SCORE = w1·LI + w2·CR + w3·Velocity + w4·Rating   │
   │            + w5·Price_Competitiveness + w6·Ad_Boost │
   │                                                      │
   └──────────────────────────────────────────────────────┘
          │            │           │          │
          ▼            ▼           ▼          ▼
   ┌────────────┐ ┌─────────┐ ┌──────────┐ ┌────────┐
   │    LI      │ │   CR    │ │ Velocity │ │ Rating │
   │(localiz.   │ │(conv.   │ │(sales/   │ │ &      │
   │ index)     │ │ rate)   │ │ 14 days) │ │ reviews│
   └─────┬──────┘ └────┬────┘ └─────┬────┘ └────┬───┘
         │             │            │            │
         └─────────────┴────────────┴────────────┘
                        │
                DASHBOARD "Ranking Health"
```

Веса `w1...w6` калибруются на исторических данных продавца (backtesting) и пересчитываются раз в 2 недели.

### 4.3. Индекс локализации (ИЛ)

#### 4.3.1. Определение

**Индекс локализации** — доля заказов, отгружаемых с того же федерального округа (ФО), в котором находится покупатель.

```
        sum(orders_i · [warehouse_region(order_i) == customer_region(order_i)])
ИЛ  =  ──────────────────────────────────────────────────────────────────────────  × 100%
                                   total_orders
```

#### 4.3.2. Уровни гранулярности

Рассчитываем ИЛ на трёх уровнях:

| Уровень | Scope | Применение |
|---|---|---|
| **L1. Account-level** | Весь кабинет | Интегральный health score |
| **L2. Category-level** | По категории (например, «Женская одежда») | Принятие решения «куда везти новую поставку» |
| **L3. SKU-level** | Конкретный артикул | Микрооптимизация для флагманов |

#### 4.3.3. Влияние ИЛ на бизнес

Эмпирически подтверждённая зависимость на платформах:

```
ИЛ < 40%  → "Красная зона":
            — Логистика дороже на 35–50%
            — Срок доставки 3–5 дней
            — Позиция в выдаче пессимизируется
            — CR падает на 15–25%

ИЛ 40–65% → "Жёлтая зона":
            — Средние тарифы
            — Срок 2–3 дня
            — Рекомендация: перераспределить поставку

ИЛ 65–85% → "Зелёная зона":
            — Оптимальные тарифы
            — Срок 1–2 дня
            — Буст в выдаче

ИЛ > 85%  → "Элитная зона":
            — Минимальные тарифы
            — Срок 1 день (экспресс)
            — Максимальный буст, бейдж "быстрая доставка"
```

#### 4.3.4. Алгоритм оптимизации распределения поставки

Задача формулируется как **целочисленная линейная программа (ILP)**:

```
ДАНО:
  W = {w_1, ..., w_n}      — склады маркетплейса
  R = {r_1, ..., r_k}      — федеральные округа со спросом
  d[r]                     — прогноз спроса на 30 дней по ФО r
  c[w→r]                   — стоимость логистики из w до r
  cap[w]                   — квота приёмки склада w
  q                        — общий объём поставки

ПЕРЕМЕННЫЕ:
  x[w,r] ≥ 0               — сколько единиц с w уйдёт в r

ЦЕЛЬ:
  minimize Σ c[w→r] · x[w,r]
  subject to:
    Σ_r x[w,r] ≤ cap[w]                  # лимит склада
    Σ_w x[w,r] ≥ d[r] · service_level    # покрытие спроса
    Σ_w,r x[w,r] = q                     # объём поставки
    ИЛ_projected ≥ target_LI             # целевой индекс локализации

РЕШАЕТСЯ: Google OR-Tools (CP-SAT solver)
```

**Что видит пользователь в UI:** карточку **"Рекомендованная поставка"** с готовой разбивкой по складам и прогнозом, как изменится ИЛ после приёмки.

### 4.4. Скорость доставки (Delivery Speed)

#### 4.4.1. Метрика TTD (Time-To-Deliver)

```
TTD_median = медиана по выборке последних 500 заказов от оплаты до выдачи клиенту
```

Система отслеживает **распределение TTD по регионам** и выявляет "дефицитные" ФО, где:
- TTD > региональной медианы конкурентов,
- И при этом доля заказов из этого ФО > 10%.

**Action:** подсветка в дашборде с рекомендацией «Добавить склад в ЦФО, сократит TTD на 1.4 дня».

### 4.5. Конверсия (CR) — воронка карточки

Разбиваем воронку на 4 шага и считаем конверсии между ними:

```
  Показы (Impressions)
        │
        │  CTR = Clicks / Impressions
        ▼
  Переходы в карточку (Clicks)
        │
        │  CR_card = AddToCart / Clicks
        ▼
  Добавления в корзину (AddToCart)
        │
        │  CR_cart = Orders / AddToCart
        ▼
  Заказы (Orders)
        │
        │  Buyout_rate = Sales / Orders   (только WB)
        ▼
  Выкупы (Sales)
```

**Триггеры алертов:**
- `CTR < median_category × 0.7` → «Плохая главная фотография или нерелевантный заголовок»
- `CR_card < 5%` → «Контент карточки слабее конкурентов»
- `CR_cart < 40%` → «Проблемы на этапе оплаты: возможно, неконкурентная цена или дорогая доставка»
- `Buyout_rate < 70%` (для одежды) → «Высокий процент отказов, проверить соответствие описания и фото»

### 4.6. Объём продаж и динамика (Sales Velocity)

Считаем **скользящее среднее за 14 дней** и сравниваем с **предыдущими 14 днями**:

```
Velocity_14d       = avg(sales_per_day[day-14 .. day])
Velocity_prev_14d  = avg(sales_per_day[day-28 .. day-15])

Trend = (Velocity_14d - Velocity_prev_14d) / Velocity_prev_14d × 100%
```

**Визуализация:**
- 📈 Зелёный спарклайн, если Trend > +10%.
- ➡️ Серый, если -10% < Trend < +10%.
- 📉 Красный, если Trend < -10% — **автоматически открывается диагностический чек-лист** (упала цена конкурента? исчезли отзывы? снизился CPM? закончился остаток на складе ЦФО?).

### 4.7. Рейтинг и отзывы

#### 4.7.1. Отслеживание
- Поллинг отзывов раз в 30 мин.
- NLP-классификация: `positive | neutral | negative | toxic`.
- Автокатегоризация причин негатива: `size_mismatch | defect | delivery_issue | packaging | wrong_item | expectation_mismatch`.

#### 4.7.2. Влияние на ранжирование
- Рейтинг < 4.5 → штраф в ранжировании и снятие бейджа «Хороший продавец».
- Рейтинг < 4.0 → пессимизация до 30% по позиции.

#### 4.7.3. Управление негативом (Review Response)

```
┌────────────────────────────────────────────────────────────┐
│  Новый негативный отзыв (rating ≤ 3) → событие в Kafka     │
├────────────────────────────────────────────────────────────┤
│  1. LLM-generator (GPT-4o-mini) создаёт 3 варианта ответа:  │
│     — эмпатичный                                             │
│     — официально-компенсаторный                              │
│     — решение проблемы (refund/replace)                      │
│                                                              │
│  2. Селлер выбирает в 1 тап с мобильного.                   │
│                                                              │
│  3. Автоответ в течение 2 часов → +0.2 к рейтингу эффекта   │
│     (эмпирически, по данным MPSTATS).                        │
└────────────────────────────────────────────────────────────┘
```

### 4.8. Дашборд «Ranking Health»

Единый экран с шестью «кольцами здоровья» (по количеству факторов), где каждое кольцо:
- **Цвет:** красный → жёлтый → зелёный.
- **Значение:** 0–100.
- **Дельта:** ±X% за 7 дней.
- **Клик** → детализация фактора с рекомендациями.

## 5. Модуль 3. Интеллектуальный прогноз поставок и сезонность

### 5.1. Постановка задачи

Классический прогноз: «сколько продадим за N дней» → `supply = daily_sales × N`.
**Проблема:** игнорирует сезонность, рекламу, ИЛ и внешние шоки. Результат — либо OOS в пики, либо заморозка оборотки в спады.

**MarketCore делает иначе:**

```
Forecast_demand(t) = Base_velocity × S(month) × P(promo) × L(localization) × E(events)
```

где:
- `S(month)` — сезонный коэффициент (см. таблицу ниже);
- `P(promo)` — коэффициент планируемых акций маркетплейса;
- `L(localization)` — корректировка на ИЛ (чем лучше ИЛ, тем выше спрос);
- `E(events)` — внешние события (блокировка конкурента, вирусный контент).

### 5.2. Таблица сезонных коэффициентов

Эта таблица — **константа бизнес-логики** (хранится в конфиге, редактируется админом в UI):

### 5.3. Алгоритм «Дней до обнуления» (OOS — Out-Of-Stock)

#### 5.3.1. Базовая формула

```python
def days_until_oos(sku, today):
    # 1. Базовая скорость продаж (медиана за 30 дней, устойчивая к выбросам)
    base_velocity = median(sku.sales_per_day[today-30:today])

    # 2. Строим прогноз на следующие 90 дней
    horizon_days = 90
    daily_forecast = []
    for d in range(horizon_days):
        date = today + timedelta(days=d)
        month = date.month

        seasonal_k = SEASONAL_COEFFICIENTS[month]
        personal_k = prophet_model.predict(sku.id, date).yhat_ratio
        final_k = 0.4 * seasonal_k + 0.6 * personal_k

        promo_k = get_planned_promo_coefficient(date, sku.category)
        li_k = get_localization_coefficient(sku)

        demand_d = base_velocity * final_k * promo_k * li_k
        daily_forecast.append(demand_d)

    # 3. Считаем, на какой день исчерпается остаток
    stock = sku.current_stock
    cumulative = 0
    for d, demand in enumerate(daily_forecast):
        cumulative += demand
        if cumulative >= stock:
            return d + 1   # День обнуления
    return None  # Остатка хватит больше, чем на horizon
```

#### 5.3.2. Учёт сроков поставки (Lead Time)

Для каждого склада определён **Lead Time (LT)** — сколько дней от заказа поставки у поставщика до приёмки маркетплейсом.

```
Supply_trigger_date = OOS_date - LT - safety_buffer

где:
  LT                = 14 дней (пример для Китая) | 3 дня (локальный склад)
  safety_buffer     = 5 дней (защита от задержек приёмки, ковровых проверок)
```

**Визуально:**

```
TODAY ──────────────────────────────────────────────→ DAYS
  │            │                    │             │
  │            ▼                    ▼             ▼
  │     Supply_trigger      Production      OOS_date
  │     (send PO today!)    complete        (stock = 0)
  │
  └── Цвет карточки в UI:
      🟢 > 30 дней до trigger   → "Всё спокойно"
      🟡 10–30 дней             → "Пора планировать"
      🔴 < 10 дней              → "СРОЧНО, отправляй PO"
      ⚫ < 0 (просрочено)        → "Вы гарантированно уйдёте в OOS"
```

### 5.4. Рекомендатель объёма поставки

```python
def recommend_supply_qty(sku, target_coverage_days=60):
    # 1. Суммируем прогнозный спрос за целевой горизонт
    projected_demand = sum(daily_forecast[:target_coverage_days])

    # 2. Вычитаем текущий остаток + товары "в пути"
    in_transit = get_in_transit(sku)
    needed = projected_demand - sku.current_stock - in_transit

    # 3. Учитываем страховой запас (15% от горизонта)
    safety_stock = 0.15 * projected_demand

    # 4. Округляем до кратного упаковке
    qty = ceil_to_multiple(needed + safety_stock, sku.pack_size)

    return {
        'qty': max(0, qty),
        'confidence': model.confidence(sku),
        'breakdown_by_warehouse': solve_ILP(qty, sku),
        'explanation': f"Прогноз: {projected_demand:.0f} ед за {target_coverage_days} дн. "
                       f"Сейчас на складе: {sku.current_stock}, в пути: {in_transit}. "
                       f"Страх. запас: {safety_stock:.0f} ед."
    }
```

### 5.5. Раннее предупреждение (Proactive Alerts)

- **Push** в 09:00 локального времени селлера, если `OOS - LT - safety < 7 дней`.
- **Weekly digest** по понедельникам: список SKU, где требуется действие на этой неделе.
- **Пиковые окна** (за 30 дней до ноября/марта/декабря) — баннер во весь дашборд: «Готовитесь к Ноябрю? 47 SKU требуют пересчёта».

## 6. Модуль 4. Управление рекламой (Hourly Bidding)

### 6.1. Философия
Ручная настройка ставок = деньги в унитаз. Рынок движется каждый час: ночью CR ниже, утром конкуренты спят, в 19:00 битва за показы. **Hourly Bidding** — это scheduler, который автоматически применяет разные ставки в зависимости от:
- часа суток;
- дня недели;
- текущего ДРР;
- конверсии в этот слот за последние 7 дней;
- остатка бюджета на день.

### 6.6. Guardrails (защитные механизмы)

1. **Дневной лимит бюджета** — запрет превышать.
2. **Максимальная ставка** — hard ceiling, редактируемый только админом.
3. **Cooldown изменений** — не менять ставку чаще, чем раз в 15 мин (против осцилляций).
4. **Dry-run режим** — первые 3 дня новое правило работает «на бумаге», показывая, что бы оно сделало, без реальных вызовов API.
5. **Kill-switch** — одна кнопка «Выключить всю автоматику» в шапке приложения.

### 6.7. A/B-тест ставок (Pro-тариф)

Делим SKU на контрольную и тестовую группы, применяем разные стратегии, через 14 дней получаем отчёт с p-value и доверительным интервалом.

### 6.8. Машинное обучение поверх правил (Phase 2)

Bandit-алгоритм (Thompson Sampling) обучается на парах `(CPM, CR, Revenue)` и предлагает **персонализированную кривую ставок** для каждого SKU. Правила остаются как human-readable интерпретация ML-решений.

## 7. Модуль 5. Unit-экономика 360°

### 7.1. Задача
Превратить «я, кажется, зарабатываю» в **точную метрику прибыли с каждой проданной единицы**, автоматически, без Excel.

### 7.2. Формула

```
Profit_per_unit = Revenue
                - Commission_mp           (комиссия площадки)
                - Logistics_fwd           (прямая логистика)
                - Logistics_return        (возвратная логистика × return_rate)
                - Storage                 (хранение × дней в среднем)
                - Acceptance              (приёмка)
                - Acquiring               (эквайринг)
                - Ad_cost                 (ДРР × Revenue)
                - COGS                    (себестоимость)
                - Tax                     (налог)
                - Operational             (упаковка, маркировка, брак)
```

### 7.3. Автоподтягивание данных

| Статья | Источник | Частота обновления |
|---|---|---|
| Commission_mp | API WB/Ozon, справочник категорий | Ежедневно |
| Logistics_fwd | API + расчёт по ИЛ и габаритам | При каждом изменении остатков |
| Logistics_return | API, `return_rate` — скользящая медиана 30 дней | Раз в сутки |
| Storage | Финансовый отчёт API | Еженедельно |
| Acceptance | Финансовый отчёт API | Еженедельно |
| Acquiring | Константа (1.8% на WB, 1.5% на Ozon) | Редактируется вручную |
| Ad_cost | Из модуля рекламы (реальный ДРР) | Реалтайм |
| COGS | Ручной ввод / импорт из 1C/ERP / CSV | При добавлении |
| Tax | Выбор режима (УСН 6%, УСН 15%, ОСНО 20%, ПСН) | Настройка кабинета |

### 7.4. Калькулятор на лету

**Сценарий:** селлер хочет понять, выгодно ли ставить цену 1290₽ вместо 1490₽.

```
┌─────────────────────────────────────────────────┐
│  Текущая цена: 1490 ₽       Новая цена: 1290 ₽  │
│  ──────────────────────     ─────────────────── │
│  Revenue:        1490       Revenue:       1290 │
│  Commission:    -268        Commission:   -232  │
│  Logistics:     -120        Logistics:    -120  │
│  Storage:        -15        Storage:       -15  │
│  Ad cost (12%): -178        Ad cost (12%):-155  │
│  COGS:          -550        COGS:         -550  │
│  Tax (УСН 6%):   -89        Tax (УСН 6%): -77   │
│  ──────────────────────     ─────────────────── │
│  Profit:         270 ₽      Profit:        141 ₽│
│  Margin:       18.1%        Margin:      10.9%  │
│                                                  │
│  ⚠️ Снижение цены на 13.4% даёт падение прибыли │
│     на 47.8%. Критично.                          │
└─────────────────────────────────────────────────┘
```

### 7.5. Break-even analysis (точка безубыточности)

Для каждого SKU система считает **минимальную цену**, при которой Profit = 0 (с учётом всех расходов):

```
P_min = COGS / (1 - commission_% - acquiring_% - tax_% - ad_%)
        + logistics_abs + storage_abs + operational_abs
```

И строит «температурную карту цен» по всем SKU:

- 🟢 Текущая цена > P_min × 1.3 → жирная прибыль
- 🟡 P_min × 1.1 < цена < P_min × 1.3 → тонкая маржа
- 🔴 Цена < P_min × 1.1 → убыточно или на грани

### 7.6. Импорт себестоимости

Три способа:
1. **CSV/XLSX загрузка** с маппингом колонок `article → cogs`.
2. **REST API** для интеграции с 1С, МойСклад, Битрикс24.
3. **Ручной ввод** (редактирование одной ячейки в гриде, bulk-update).

### 7.7. P&L отчёт и экспорт

Еженедельный/ежемесячный PDF-отчёт с детализацией:
- Top-10 прибыльных SKU
- Top-10 убыточных SKU
- Распределение расходов (pie chart)
- Динамика маржинальности (line chart)
- Сравнение с предыдущим периодом

## 8. Модуль 6. UI/UX концепция Luxe Noir

### 8.1. Философия визуального языка
**Luxe Noir** — это не просто «тёмная тема». Это отказ от визуального шума в пользу **оперативной плотности информации**. Инспирация: терминалы Bloomberg, интерфейсы Linear, финансовые дашборды Stripe.

## 11. Безопасность и хранение токенов

### 11.1. Угрозы и митигации

| Угроза | Митигация |
|---|---|
| Утечка API-ключа WB/Ozon | Envelope encryption через AWS KMS / Vault Transit; ключи в БД зашифрованы, дешифровка только в памяти сервиса |
| SQL-инъекции | ORM с параметризованными запросами (SQLAlchemy / Prisma); статический анализ (Semgrep) |
| XSS в UI | Строгая CSP, React экранирует по умолчанию, никаких `dangerouslySetInnerHTML` |
| CSRF | SameSite=Strict cookies + double-submit token |
| Brute-force на логин | Rate-limit 5 попыток/мин на IP + recaptcha v3 |
| Session hijack | Refresh-токен с rotation, short-lived access token (15 мин) |
| Кражу 2FA-устройства | Резервные коды + опциональный WebAuthn (phase 2) |
| Привилегированный доступ | RBAC: `owner | admin | manager | viewer`, аудит всех действий |
| SSRF при парсинге | Allowlist доменов (wildberries.ru, ozon.ru), выделенный egress-шлюз |
| Insider threat | Логирование всех действий в immutable log (S3 + Object Lock) |

### 11.2. Multi-tenancy изоляция

- Row-Level Security в PostgreSQL (`RLS: current_account_id = current_setting('app.account_id')`).
- Проверка `account_id` на уровне API-gateway (middleware).
- Запрет cross-account запросов, юнит-тесты покрывают 100% critical paths.

### 12.2. Milestone breakdown

- Базовый ingestor: заказы, остатки, цены.
- Минимальный дашборд: 4 KPI + таблица SKU.

**M2-M3: MVP-1 / Observability**
- Полный ingestor (реклама, финансы, аналитика).

- Unit-экономика (ручной ввод COGS).
- Парсинг конкурентов (SKU-watchlist).
- Мобильная PWA.

**M4-M5: Beta / Automation**
- Hourly Bidding с 6 предустановленными стратегиями.
- Индекс локализации + ILP-оптимизатор поставок.
- Прогноз OOS с сезонными коэффициентами.
- Интеграции: Telegram-бот алертов, webhook для ERP.

**M6: Public launch / Polish**
- A/B-тест ставок.
- Review management (авто-ответы).
- Billing + тарифная сетка.
- Партнёрская программа.
- Публичная документация API.

**M7-M9: v1.1 / Intelligence**
- ML-ассистент (bandit для биддинга).
- Расширенная аналитика конкурентов (keyword-based).
- Native mobile apps (Capacitor).
- Локализация EN/KZ.
- White-label для агентств.
